# AI

`@cslug/ai` turns AI features into ordinary cslug code: agents and tools are `@inject()` classes, inputs and outputs
are validators, long runs are jobs, tests use a fake. The design is in [docs/ai-readiness.md](../docs/ai-readiness.md).

> The MVP does not include AI features. This guide shows the first ones that would pay off, so the API can be
> judged now and the seams kept in place.

## Configuration

```ts
// config/ai.ts
export default defineConfig({
  default: 'anthropic',
  providers: {
    anthropic: { driver: 'anthropic', apiKey: env.ANTHROPIC_API_KEY },   // promptCaching, fallbacks: on by default
    local: { driver: 'openai-compatible', baseUrl: 'http://localhost:11434/v1' },
  },
  models: {                                   // code refers to roles, never to model IDs
    fast: 'claude-haiku-5-5',
    smart: 'claude-opus-5-5',
  },
})
```

`cslug add ai` installs the package, adds `AiProvider` and writes this file. The Anthropic driver calls the Messages
API with `fetch` (cslug has no third-party runtime dependencies): the system prompt is cached (`promptCaching:
false` to turn it off), and on the models that support them, refusals fall back server-side to another model
(`fallbacks: false` to turn it off). A refusal that is not rescued is an `AiRefusalError`.

A daily budget caps what the app spends:

```ts
budget: { perDay: { usd: 10 }, alertAt: 0.8 },
```

Each call is charged at the model's price (built in for Claude models; `prices` adds others). Once the day's spend
reaches the limit, runs fail with `AiBudgetError` until the next day; at 80% `AiBudgetAlert` is emitted once, so a
listener can warn the team. The spend lives in the cache, shared by every process when Redis is installed.

Embeddings for semantic search (`@cslug/search`) come from the same file: `embeddings: { driver: 'voyage', model:
'voyage-3.5' }` (or any OpenAI-compatible `/embeddings` API, Ollama included). Their calls count against the budget
too; add their price to `prices`.

## Structured output: turning an operator's reply into a comparable offer (MVP #3)

Operators answer trip requests on WhatsApp in free text. The team copies those into a standard proposal by hand.
An agent can draft that step; staff review it.

```ts
// app/validators/operator-offer-schema.ts — shared by the admin form and the agent
export const OperatorOfferSchema = v.object({
  price: v.money(),
  inclusions: v.array(v.enum(['accommodation', 'meals', 'park_fees', 'guide', 'fuel', 'driver'])),
  vehicle: v.object({ type: v.enum(['4x4', 'minibus', 'car']), seats: v.int() }),
  guideLanguages: v.array(v.enum(['fr', 'en', 'it', 'de'])),
  nightDriving: v.boolean().describe('True if any leg is planned after dark'),
  notes: v.string().max(500).optional(),
})
```

```ts
// app/agents/offer-extractor-agent.ts
import { inject } from '@cslug/core'
import { Agent, prompt } from '@cslug/ai'
import { OperatorOfferSchema } from '#app/validators/operator-offer-schema'

@inject()
export class OfferExtractorAgent extends Agent {
  model = 'fast'                                          // a role from config ai.models, or a model ID
  instructions = prompt('proposals/extract-offer')       // resources/prompts/proposals/extract-offer.md
  output = OperatorOfferSchema
}
```

Like jobs, agents declare their settings without `override`: `model`, `instructions`, `output`, `tools`,
`maxSteps` (8), `provider`, `effort`, `maxTokens`. With `output`, the schema becomes the model's structured-output
format (constraints the API does not accept, such as `min` or `max`, are left out of what it is sent) and the
answer is parsed and validated with the full schema.

```ts
const offer = await this.extractor.run({ input: reply.text, context: { currency: tripRequest.budget.currency } })
//    ^? v.infer<typeof OperatorOfferSchema>  — parsed and validated; AiOutputError if the model can't comply
```

Prompts are Markdown files filled from `context` on every run, versioned in git and listed by `cslug ai:prompts`:

```md
<!-- resources/prompts/proposals/extract-offer.md -->
You read an operator's reply about {{ trip.circuit.name }} for {{ trip.groupSize }} travellers.
Prices are in {{ currency }}; answer in {{ language | English }}.
Inclusions the traveller asked for:
{{ trip.wishes }}
```

- `{{ trip.circuit.name }}` reads a nested value; an object or a list (`trip.wishes`) is written as JSON.
- `{{ language | English }}` falls back when the value is missing or null.
- A value missing without a default is an error naming every missing one, so a prompt never goes out half filled.

Instructions can also be built in code: `instructions = (context) => …` returns a string or a `prompt(...)` (filled
from the same context), and may be async:

```ts
instructions = async ({ operatorId }: Record<string, unknown>) =>
  (await this.operators.prefersShortReplies(String(operatorId))) ? prompt('replies/short') : prompt('replies/full')
```

In a conversation, the prompt is filled again on every turn: changing a value between turns changes the system
prompt, so the provider can no longer reuse the conversation's prompt cache. Keep per-turn data in the input and
values that rarely change in the context.

## Tools: letting an agent act through your code

```ts
// app/tools/find-operators-tool.ts
import { inject } from '@cslug/core'
import { Tool } from '@cslug/ai'
import { v } from '@cslug/validation'
import { OperatorRepository } from '#app/repositories/operator-repository'

@inject(OperatorRepository)
export class FindOperatorsTool extends Tool {
  name = 'find_operators'
  description = 'List verified operators for a circuit with rating and vehicle types.'
  input = v.object({ circuitId: v.uuid(), groupSize: v.int().min(1) })

  constructor(private operators: OperatorRepository) { super() }

  async handle({ circuitId, groupSize }: v.infer<this['input']>) {
    const list = await this.operators.verifiedOn(circuitId)
    return list.filter((o) => o.maxSeats >= groupSize).map(operatorTransformer)
  }
}
```

```ts
@inject()
export class TripRequestTriageAgent extends Agent {
  model = 'smart'
  instructions = prompt('trip-requests/triage')
  tools = [FindOperatorsTool, CircuitDetailsTool]
  output = v.object({ circuitId: v.uuid(), shortlist: v.array(v.uuid()).max(3), questionsForTraveller: v.array(v.string()) })
  maxSteps = 6
}
```

Tools run with the **current user's** permissions (they can call `auth.authorize`), inside the agent run's scope.
Their input is validated before `handle` runs; an invalid input or a thrown error goes back to the model as an
error result, so it can correct itself. All the calls of one turn run together and go back in one message.

## Searching from an agent

An agent can search an index (`@cslug/search`) through a ready-made tool:

```ts
@inject()
export class VisaAssistantAgent extends Agent {
  model = 'smart'
  instructions = prompt('help/visa')
  tools = [searchTool(helpIndex, { description: 'The help center: visas, vaccines, packing', perPage: 5 }), recallTool()]
}
```

- `searchTool(index, { name, description, perPage, filter, words })`: the model sends `{ query, page? }` and reads
  the best matches with a plain-text snippet each (hybrid when the index is semantic). `filter` always applies.
- `recallTool()`: with `ai.recall: true` in `config/ai.ts`, stored conversations' messages are also kept in an index
  (`ai-conversations`; by meaning when an embedder is configured). The tool searches the **current conversation's
  owner's** other conversations, whatever the model asks: one user never sees another's. Deleting a conversation
  removes it from recall.

## Long runs are jobs

```ts
@inject(TripRequestRepository, TripRequestTriageAgent, ProposalService)
export class DraftProposalJob extends Job<{ tripRequestId: string }> {
  static queue = 'ai'
  static tries = 2
  constructor(
    private tripRequests: TripRequestRepository,
    private agent: TripRequestTriageAgent,
    private proposals: ProposalService,
  ) { super() }

  async handle({ tripRequestId }) {
    const tripRequest = await this.tripRequests.findOrFail(tripRequestId)
    const draft = await this.agent.run({ input: describeTripRequest(tripRequest) })
    await this.proposals.saveDraft(tripRequestId, draft, { reviewedBy: null })    // staff must approve
  }
}
```

## Streaming to a page

```ts
async assist({ request }: HttpContext) {
  const { question } = await request.validate(v.object({ question: v.string().max(500) }))
  return sse(this.visaAssistant.stream({ input: question }))     // text deltas as server-sent events
}
```

`sse` comes from `@cslug/ai`: each piece of text is a `data:` line (a JSON string), the end is `event: done`, a
failure `event: error`. The stream keeps the request's context (user, scope) while the model answers; tools run
between the streamed turns.

## Conversations

A run answers one input. To continue a conversation, pass the previous result's `messages` as `history`:

```ts
async ask({ request, session }: HttpContext) {
  const { question } = await request.validate(v.object({ question: v.string().max(500) }))
  const answer = await this.visaAssistant.result({ input: question, history: session.get<Message[]>('visa') ?? [] })
  session.put('visa', answer.messages)          // the whole exchange, tool rounds included
  return { answer: answer.value }
}
```

`result()` is `run()` in detail: `value`, `messages`, `usage`, `costUsd`. A stream gives the same once it has been
read: `const stream = agent.stream({ input, history })`, return `sse(stream)`, and store `(await stream.result).messages`
in a listener or after the response. Messages are plain JSON, so they can be kept in a session, a `jsonb` column or
anywhere else; send them back unchanged. History only grows, which lets the Anthropic driver serve the earlier turns
from the prompt cache.

### Stored conversations

With `@cslug/database`, `Conversations` keeps them for you (`cslug migrate` creates the `cslug_ai_*` tables):

```ts
@inject(Conversations)
export class VisaChatController {
  constructor(private conversations: Conversations) {}

  async store({ request }: HttpContext) {                       // POST /visa-chats
    const { question } = await request.validate(v.object({ question: v.string().max(500) }))
    const chat = await this.conversations.start(VisaAssistantAgent, { title: question.slice(0, 80) })
    return { id: chat.id, answer: (await chat.send(question)).value }
  }

  async reply({ request, params }: HttpContext) {               // POST /visa-chats/:id
    const { question } = await request.validate(v.object({ question: v.string().max(500) }))
    const chat = await this.conversations.find(VisaAssistantAgent, params.id)   // 404 unless it is yours
    return sse(chat.stream(question))                           // stored once streamed
  }
}
```

- A conversation belongs to the signed-in user who started it; `find` answers 404 to anyone else, so ids are never
  confirmed to strangers. A job, which has no signed-in user, names the owner: `find(Agent, id, { owner: user })`.
  Other owners take a type: `start(Agent, { owner: team, ownerType: 'team' })`. `owner: null` makes a conversation
  anyone with its id can continue (a guest chat whose id you keep in the session).
- `list()` gives the user's conversations, most recent first; `chat.messages()`, `chat.update({ title, metadata })`,
  `chat.delete()`.
- Two turns sent at once can't interleave: the second to finish is a `ConflictError` (409).
- Long conversations are compacted by the provider (Anthropic summarises the earlier turns past about 150K tokens,
  on the models that support it); `compact = false` on the agent turns it off.

Every run, in a conversation or not, is also recorded in `cslug_ai_runs`: agent, model, user, tokens, estimated cost,
status and error. `ai.runs: false` turns that off.

## MCP

Expose tools to external AI clients (staff using Claude Desktop, partner agents). Tools in `app/tools/` marked with
`@mcp()` are served:

```ts
@inject()
@mcp({ ability: 'mcp:bookings' })          // an API token with this ability (session users pass)
export class BookingStatusTool extends Tool { … }

@inject()
@mcp({ public: true })                     // anyone; without options: any authenticated caller
export class CircuitListTool extends Tool { … }
```

- **HTTP:** `POST /mcp` on the web server (streamable HTTP, JSON responses). It runs the api group's middleware, so
  an API token (`Authorization: Bearer …`) identifies the caller; a client sees and calls only what it may (a hidden
  tool is "unknown"). A request from another `Origin` than `app.url` is refused (403).
- **stdio:** `cslug mcp:serve`, for a local client (`{"command": "bunx", "args": ["cslug", "mcp:serve"]}`): every
  exposed tool, since the caller is whoever runs the command. Logs go to stderr.

The server speaks the current protocol (2026-07-28: `server/discover`, the version on every request) and the
`initialize` versions before it (2025-11-25, 2025-06-18, 2025-03-26), so current and older clients connect. A
tool's input is validated with its schema; an invalid input or a thrown error is an error result the client's model
can read.

Use an external MCP server from an agent: `tools = [...mcp('maps').tools(['route_duration'])]`, with the server in
`config/ai.ts`:

```ts
mcp: {
  maps: { url: 'https://maps.example/mcp', headers: { authorization: `Bearer ${env.MAPS_TOKEN}` } },
  files: { command: ['bunx', 'some-mcp-server'] },        // stdio: started on first use, stopped at shutdown
},
```

The client asks `server/discover` first and falls back to `initialize` for older servers (keeping their session id).

## Testing

```ts
const app = testApp({ fakes: ['ai'] })
app.ai.respond(OfferExtractorAgent, { price: { amount: 210000n, currency: 'EUR' }, inclusions: ['guide'], … })

await app.resolve(DraftProposalJob).handle({ tripRequestId })
app.ai.assertRan(OfferExtractorAgent, (run) => run.input.includes('Isalo'))
```

`respond()` answers are checked against the agent's `output` schema, so fixtures stay valid; an agent with no answer
fails with the line to add.

A recorded answer keeps a test realistic without calling the model on every run:

```ts
app.ai.fixture(OfferExtractorAgent, 'proposals/isalo-offer')   // tests/fixtures/ai/proposals/isalo-offer.json
```

```bash
cslug ai:record tests/jobs/draft-proposal-job.test.ts   # calls the real model for the missing fixtures, writes them
cslug ai:eval proposals                                 # after a prompt change: same / diff / schema failure per fixture
```

`ai:record` runs the test against the real provider once and stores the answer (with the input and context), so the
suite stays fast and deterministic (`--all` re-records). `ai:eval proposals` runs `tests/fixtures/ai/proposals/`
through the real model and reports schema failures and diffs, which keeps prompt changes reviewable; schema failures
fail the command (diffs too with `--strict`). Both cost what the calls cost.
